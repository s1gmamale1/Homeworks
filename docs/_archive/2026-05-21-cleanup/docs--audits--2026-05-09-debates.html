TL;DR

Two debates, 23 proposals, no production code touched. The Flow swarm reviewed homework cycle interactivity, content quality, and Uzbek grammar; 3 ship as-is, 3 ship modified, 1 deferred, 1 rejected. The Game swarm reviewed 14 gamification proposals; 6 ship, 3 modified, 3 deferred, 2 rejected.

The single highest-leverage move across both debates is G9 — Why Was I Wrong tap (XS effort, 5/5 pedagogy, zero schema risk, data already in payload). The most consequential rejection is the seductive 1-line "resurrect Memory Match" — spot-checking proved it would cause a runtime DOM collision with Tile Match, not a no-op. The most under-appreciated cross-cutting risk is the overjustification effect: stacking XP persistence + streaks + heatmaps + growth echoes turns intrinsic motivation into number-chasing. Ship at most one Cat-4 reward in v1.

Combined plan: ~12–14 dev-days across 7 sequenced PRs. Two open decisions block sequencing — Memory Match (delete vs. refactor) and Cat-4 reward selection (G13 alone, or none).

Flow Debate

3-agent swarm — Recon → Reformer → Skeptic — reviewing the homework flow against three user complaints: lack of interactivity, boring/raw content, Uzbek grammar errors. Sub-docs: recon, reform, skeptic.

Current state — 4 facts that matter

Common backbone (all 7 subjects). preview → flashcards → memory-sprint → game-breaks → [maybe consolidation/real-life] → final-challenge → reflection. Math has Easy/Hard branching (5/8 phases). History is always Hard (6 phases, no Real-Life because the narrative IS the content).

Game inventory mismatch. 8 game slots in gbActiveGameOrder() (template line 12666). Memory Match (mm) is specced in flow.md for math/history/biology/physics but has no routing entry and no panel HTML (#gb-panel-mm = 0 grep hits).

Interactivity profile. Preview = read-only · flashcards = tap-flip (no correctness signal) · memory-sprint = MC/TF tap · game-breaks = varied (Adaptive Quiz / Tile Match / Sentence Fill) · real-life = typed · final-challenge = typed + boss · reflection = read-only. Half the cycle is one-way.

Uzbek surface. Every phase generates Uzbek. Zero post-generation grammar check. Zero "self-check Uzbek" rule in any of the 7 instruction.md files. The complaint is structurally correct.

Issues — 5 the swarm confirmed

  1. Mislabeled mechanic (P2). Slots 1 (wc) and 6 (sf) both display "Sentence Fill" to students — but wc is the GB_WHY_CHAIN causal scaffold, not Sentence Fill. Two different mechanics, same label. Suppresses adoption and confuses students.
  2. Broken Preview→Reflection contract (P3). Preview ends with a BOST goal prompt ("Bugun … nimani bilmoqchisiz?") that the student reads but never answers. Reflection-coach is told to "resurface it" — it has nothing to resurface.
  3. Two-layer panel content collapsed visually (P4). Preview prompts mandate "Qatlam 1 — Rasmiy izoh" + "Qatlam 2 — Sodda so'zlar" — but the runtime renders them as flat text, indistinguishable. Wall-of-text visual = "boring/raw" complaint, confirmed.
  4. Flashcard phase has zero correctness signal (P5). The only graded-style phase with no graded output. Student flips card, moves on; the cycle never knows if they knew it.
  5. English has no flow.md (P6). Only subject without a canonical flow spec. Every future English work re-derives from instruction.md. Drift risk = real.

Real fix: build #gb-panel-mm + refactor MM to use mm-prefixed IDs (~80 LOC) — or delete the dead code (aligns with the "engine simplification" theme from yesterday's MASTER audit).

Verdict. Reject the 1-line version. Two paths forward: (a) deliberate medium-cost refactor IF you actually want MM live, or (b) delete gbInitMM + GB_MEMORY_MATCH constant as dead code. Pick "delete" unless there's a pedagogical reason MM beats TM/MP for a specific phase.

P3. BOST goal as interactive micro-prompt 🛠️ Ship modified

Why. Preview ends with a BOST learning-goal prompt that students read passively. Reflection is told to surface it but nothing was captured. How. Add an input field below BOST → store in __sessionLog → reflection-coach echoes it back. What. 15-second interaction at end of Preview, personalized callback in Reflection.

Skeptic counter. __sessionLog does not exist (grep: 0 hits). The Reformer invented the storage. Reflection-coach prompt also has no bost_goal slot — wiring it changes the runtime AI-context contract. Real cost is M, not S.

P4. "Sodda so'zlar" CSS toggle ⏳ Defer

Why. Preview panels mandate two-layer (formal + plain) text but render flat. Wall-of-text problem. How. Detect literal phrase "Sodda so'zlar bilan:" → apply collapse + toggle CSS class. What. XS fix, no backend, makes panels visibly less raw.

Skeptic counter. Spot-check confirmed math uses "Sodda so'zlar bilan:" but history uses "Qatlam 2 — Sodda so'zlar:" (different phrase, no bilan, wrapped in bold). Worse: in real content_json, the layer-2 text is inside the same p block as layer 1 (same <strong> boundary). The Reformer's structure assumption is wrong — there's no separate block to tag. Heuristic mis-fires on history; structure mis-fires across the corpus.

Verdict. Defer — don't ship the regex heuristic. Do prompt-side standardisation first: update all 7 preview prompts to emit Layer 2 as its own p block with a stable marker ({type: "p", layer: 2, text: "..."}). Schema-additive (allowed). Then the toggle ships on a stable marker, not regex. Two PRs: prompt-standardise (S) → toggle (XS). Together M.

P6. Create english/flow.md ✅ Ship

Why. English is the only subject without flow.md; instruction.md is the only spec; drift risk. How. Copy math-algebra/flow.md structure + populate from existing english/instruction.md. What. 7-of-7 subjects have a canonical flow spec.

Skeptic counter. Concedes. One-liner risk: don't let it become a 4-hour Reading-phase semantics debate. Time-box 90 min.

Verdict. Ship as XS hygiene fix. Bundle with P7 + P8 in a single grammar-quality PR.

P7. Uzbek grammar rules in instruction.md 🛠️ Ship modified — bundle, don't ship alone

Why. Zero grammar gate exists. Cheapest fix: tell the LLM what NOT to do at generation time. How. Add a ## Uzbek Grammar Quality Rules section to all 7 instruction.md files (6–8 bullet rules: script consistency, "Siz" agreement, no Russian proxies, verb-final order, etc.). What. LLM self-corrects before output.

Skeptic counter. Real but oversold. Research: GPT-class models follow targeted system-prompt constraints at ~60–80%, degrades sharply at 4k+ token context (common in our preview prompts). Kimi K2.6 has zero published Uzbek-morphology benchmarks — we're guessing. After P7, residual error rate is 20–40% of current → the new bug surface, harder to debug because the prompt now CLAIMS the rules are enforced. Worse: the Reformer's specific rule "verb-final: subordinate clauses end with -b/-ib/-gan/-adigan" is linguistically wrong — these aren't interchangeable. Wrong rules are worse than no rules.

Verdict. Ship modified — (1) bundle with P8 (catch-net for residual), (2) a native Uzbek linguist signs off on every rule before merge, (3) A/B test: 20 homeworks before, 20 after, blind native-speaker scoring. If P7 alone moves the mean by less than 0.5 points, it's theatre.

P8. Injector-layer regex grammar check ✅ Ship — bundle with P7

Why. P7 reduces but doesn't eliminate errors. Regex catch-net at the injector layer for the residual. How. _uzbek_quality_check(content) in server/services/injector.py — returns warning list (Cyrillic / "sen " / empty blocks / panel count). Logged via logging.warning(), never blocks the student. What. Every generation produces a warning trail; "sen" leaks become visible.

Skeptic counter. Concedes the catch-net design. Two improvements: (1) \bsen(?:ing|ga|i)?\b word-boundary regex (the Reformer's r"sen\s" misses cases and can false-positive); (2) pipe warnings to the builder UI homework-detail view, not just log — logged warnings rot. Adds ~20 LOC, turns logging into a tight feedback loop.

Verdict. Ship with the word-boundary regex + builder-UI surfacing. Bundle with P7 + P6 in one "Uzbek quality" PR.

Cross-cutting risks the Reformer underweighted

  • Phantom storage (__sessionLog). Referenced in P3 + P5 as if it exists. It doesn't. Both fixes route through sessionStorage.
  • "No schema change" claimed too easily. P3 changes the AI-context contract; P4 implies a schema convention. The frozen-schema invariant covers content_json, but the runtime AI-prompt contract is also a contract.
  • Prompt instructions ≠ enforcement. P7-style "tell the LLM not to do X" needs measurement (A/B + adherence numbers), not just intent.
  • Missing regression tests. The Reformer specifies tests for P1/P2/P8 but is silent on P3/P4/P5. Project rule (CONTRIBUTING.md) requires every fix ship a regression test.

Game Debate

3-agent swarm — Inventor (Sonnet) → Pedagogy Critic (Sonnet) + Feasibility Realist (Opus). 14 proposals debated. Sub-docs: Inventor's slate, Pedagogy review, Feasibility review.

Headline: G9 — Why Was I Wrong tap is the single cheapest highest-pedagogy win in the slate. Corrective feedback is the most-evidenced cognitive-science intervention; the data already exists in the explain field; pure runtime fix. The Pedagogy critic disagreed sharpest with G6 (Flashcard Confidence Tap) — Dunning-Kruger problem: lowest-knowledge students self-assess worst. Ship-as-is is acceptable IF paired with G9 corrective-feedback so the cycle has both self-signal AND truth-signal. The Feasibility critic caught: G7 (Preview Curiosity) is S not XS; G2 drag-rank is M-high not M; G14 reads a phase_scores column that has zero writes anywhere in the codebase.

Cross-cutting risks (read first)

1. Overjustification effect (the strongest cross-cutting catch). Cat 3 + Cat 4 (G10 / G11 / G12 / G13) shipped together create a layered reward stack: XP persists → Streak counts → Heatmap shows history → "You've grown" phrase → student optimizes for the numbers, not the learning. Each individually is defensible. Stacked, they crowd out the intrinsic motivation already present in the boss mechanic. Recommendation: ship at most ONE of G10 / G11 / G12 / G13 in v1. G10 is the right pick because it's pure infrastructure — it ENABLES the others without activating the full reward stack yet. Decide which (if any) of G11 / G12 / G13 to add only after measuring G10's actual effect on completion + boss-replay rates.

2. Schema vs. runtime-contract distinction. The frozen-schema invariant covers content_json only. Several proposals don't add content_json keys but DO extend other contracts: G10 adds sessions.boss_xp_earned column (DB schema change, but OUTSIDE content_json — allowed); G7 would inject memory-sprint content into preview-phase tutor context, bypassing _redact_question_for_tutor (the answer-leak invariant) — reject as proposed; G3 / G6 / G8 all touch the runtime payload contract subtly — must include regression tests per the CONTRIBUTING rule.

3. The "free reads existing X" trap. G14 claims it reads existing phase_scores. Truth: that column has zero writes anywhere in server/. Reading it returns null. So G14's "XS — reads existing data" is wrong; real cost is S+ because phase_scores writes need to be wired first (a separate non-trivial task).

Verdict. Ship first. Lowest cost in slate, highest pedagogy score, zero risk.

Verdict. Ship modified — gate the implementation on a content-quality checklist for builders (every analogy pair must include 4 plausible distractors, not 1 right + 3 obvious wrong). Without that, G3 ships as engagement theatre.
